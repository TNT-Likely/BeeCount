# GitHub PR 验收包附件

用户已要求把验收包自动附到 PR 时使用。完整结果通过独立附件交付，PR 描述保留摘要和下载入口；ZIP、截图和 JSON 不进入源码提交。

## 上传和发布

1. 核对目标 PR、对应源码 SHA 和待上传包。打包前脱敏，解压检查文件 manifest 与校验表，计算 ZIP 自身的 SHA256。固定这个包，上传后不重新生成同名包替换其内容。
2. 检查当前工具和 GitHub 支持的附件类型与大小。CLI/API 不支持 ZIP 时，检查网页的文件选择入口，不据此判定只能由用户手动上传。GitHub 网页当前支持最多 25MB 的 ZIP，执行时以[官方附件说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)为准。
3. 通过可用的浏览器工具打开目标 PR，核对登录账号和写权限。已有 GitHub 登录可复用；未登录时交给用户完成登录。先阅读所用浏览器工具的操作说明，再使用真实网页控件。
4. 点击评论编辑器的「Add files / 附加文件」，通过系统文件选择器设置本地 ZIP。无需模拟拖拽，也不通过读取 cookie、会话或内部上传接口代替网页操作。工具支持文件选择事件时，先监听该事件，再点击上传控件。
5. 等待「Uploading…」变成 GitHub 附件 Markdown 链接。附件链接可以直接写入 PR 描述，无需另发评论。若使用评论编辑器准备附件，发布描述后清空本次临时草稿，避免重复评论。
6. 使用刚读取的最新 PR 描述，增加「独立验收包」段落，包含 ZIP 下载链接、解压打开 `index.html` 的说明、对应 App/Cloud SHA 和 ZIP SHA256；保留已有说明和用户编辑。更新后查看实际渲染的描述，确认链接已显示。
7. 发布后回下载附件，对比大小与 SHA256，并检查 ZIP 可读取。记录 PR URL、附件 URL、文件名、对应源码、校验结果和交付截图。附件回执留在包外，避免改变已发布 ZIP 的哈希。

收到附件 URL 只表示上传环节已完成。发布描述前附件可能暂不可下载；以发布后链接可访问、回下载哈希一致作为交付完成的证据。

## 失败边界

- 安全或权限拦截时停止该操作并说明；不通过换浏览器、读取会话或绕过安全限制继续。
- 下载失败或超时时先确认附件已发布、链接可访问，避免反复上传同一个包。可有限重试实际失败的环节；仍失败则保留本地完整包和具体原因。
- 已上传但无法核对下载时，分别报告「已上传」和「下载校验未完成」，不能宣称整条流程已验证成功。
- 浏览器不可用、需要用户登录或网站拒绝附件时，说明当前阻碍。创建独立验收仓库、Release 或其他托管需要另外的授权，不作为默认替代方案。

## 关联 Issue

核对关联 Issue 的实际需求，再在 PR 描述链接它们。混合多个需求的 Issue 要注明本次覆盖部分；完整解决且授权范围允许时才使用自动关闭关键词。仅关联某一部分不意味着整个 Issue 可以关闭。
