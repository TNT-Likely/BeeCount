# BeeCount PR 验收证据交付

使用 [隔离验收 skill](../isolated-app-cloud-qa/SKILL.md) 交付的独立报告、合成截图与 ZIP。从 [PR 验收交接](../isolated-app-cloud-qa/references/pr-lifecycle.md) 接续同一轮验收。

## 接续发布

- 已获授权交付 PR 的隔离验收，报告校验完成后直接执行本技能的发布步骤。也可独立补发既有报告。缺少可核对的结果时，先找既有报告，按用户授权判断是否补测。
- 通过交接脚本按轮次和 ZIP SHA256 查询已保存的主报告、引用和附件 URL。每取得一个附件 URL 即记录上传。

## 选择报告所在的 PR

- 同一份联调报告选一条已授权且相关审查者可访问的 PR 发布。优先复用已发布的报告或有上传回执的 PR。尚未发布时按用户指定选择，App 界面为主要验收入口时默认放在 App PR，其他任务按主要改动选择。
- 其余关联 PR 写本仓改动、依赖、实测提交、相关验证和范围，再链接到完整报告所在的 PR。共享报告的正文、截图和附件只在主报告 PR 发布一次。各仓有不同的验收报告时，分别交付各自的证据。
- 发布前确认目标 PR 和附件的访问范围。跨公开与私有仓库时，按用户授权核对可以共享的内容与报告链接，再决定主报告所在位置。

## 核对待交付证据

- 读取目标仓库、PR 编号、最新描述和 head SHA。对照报告中对应仓的源码 SHA；多仓联调时保留各仓分别验过的版本。PR 后续提交应与报告的实测版本区分。
- 预先打开报告和待发布的截图，核对公开范围。排除原始日志、凭证、真实用户数据、应用二进制和私人路径。用 `unzip -t` 检查 ZIP，解压到私有临时目录核对 manifest 与 `SHA256SUMS`，计算 ZIP 自身 SHA256。后续上传、复核及回执均引用这份固定文件。
- 用同一份脱敏验收数据生成 GitHub Markdown。复用已有报告时按已核验的 HTML 和截图整理，保留逐项结果、数据对照、覆盖范围和限制。正文默认展示关键截图，其余截图与技术附录可用 `<details>` 折叠。原版 HTML 的样式随附件保留。

## 在 GitHub 发布

1. 在主报告 PR 的描述编辑器中使用「Paste, drop, or click to add files」上传核验过的独立 HTML、ZIP 和正文使用的截图。已有附件在实测 SHA 与 ZIP SHA256 匹配时复用。支持多选时可将本次待上传文件放在专用目录，再核对选中文件。类型或大小有疑问时查看 [GitHub 官方附件说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)。
2. 上传占位符变成附件链接后立即登记。读取最新 PR 正文，将 Markdown 报告写入本轮受管验收区。保留原有改动、用户编辑、其他附件和 Issue 关联。报告链接原版 HTML 和 ZIP，注明解压后打开 `index.html`，并写各仓实测 SHA 和 ZIP SHA256。若使用同一 PR 的评论编辑器暂存链接，发布描述后清理本次临时草稿。
3. 核验主报告的实际渲染、截图和附件。从已发布链接回下载 HTML 与 ZIP，比对大小和 SHA256，再校验 ZIP 可解压。回执记录在 ZIP 外，供后续补发与合并接续。
4. 主报告验证后，在已授权的其他关联 PR 正文补充本仓验收摘要及主报告链接，核对线上显示与链接目标，用 `delivery ... reference --value <主报告 PR URL>` 登记引用。接续时读取当前报告哈希下的引用，按主报告回执补齐缺失证据。

## 异常处理

网页会话未登录时，按当前客户端流程复用已有登录会话或交接登录。GitHub API 或 CLI 可维护正文。附件上传或回下载受阻时，仍可发布已核验的 Markdown 结果，并在交接记录中保存已有链接、具体阻碍与本地证据。重试前重新读取对应 PR 正文和 head，按回执补齐缺项。
