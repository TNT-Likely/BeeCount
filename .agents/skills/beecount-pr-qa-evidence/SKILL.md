# BeeCount PR 验收证据交付

使用 [隔离验收 skill](../isolated-app-cloud-qa/SKILL.md) 交付的独立报告、合成截图与 ZIP。缺少可核对的结果时，先定位既有报告，按用户授权选择是否运行缺失的验收。上传授权应覆盖目标 PR 和对应证据。

## 核对待交付证据

- 读取目标仓库、PR 编号、最新描述和 head SHA。对照报告中对应仓的源码 SHA；多仓联调时保留各仓分别验过的版本。PR 后续提交应与报告的实测版本区分。
- 预先打开报告和代表性截图，核对公开范围。排除原始日志、凭证、真实用户数据、应用二进制和私人路径。用 `unzip -t` 检查 ZIP，解压到私有临时目录核对 manifest 与 `SHA256SUMS`，计算 ZIP 自身 SHA256。后续上传、复核及回执均引用这份固定文件。
- ZIP 保留完整 HTML、截图和技术附录，证据文件通过附件交付并留在本地忽略目录。PR 正文展示能说明操作和结果的截图，配简短说明。按用户指定的截图或范围交付，并核对已有验收段落和附件，避免重复上传或发重复评论。

## 在 GitHub 发布

1. 在已有登录且能编辑目标 PR 的浏览器会话中打开描述编辑器，使用「Paste, drop, or click to add files」或页面提供的文件选择入口。通过系统文件选择器提交核验过的文件。支持多选时可将本次待上传文件放在专用目录，再核对选中文件。附件类型或大小有疑问时查看 [GitHub 官方附件说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)。
2. 等待上传占位符全部变为真实附件链接，再整理正文。优先使用 PR 描述编辑器；若使用同一 PR 的评论编辑器暂存链接，发布描述后清理本次临时草稿。使用刚读取的描述，保留原有改动、验收范围、用户编辑、其他附件和 Issue 关联，只补充本次证据。描述包含 ZIP 链接、解压打开 `index.html` 的说明、实测 SHA、ZIP SHA256 与带说明的内嵌截图。
3. 保存并检查实际渲染的描述，确认报告和截图链接都已发布、图片可见。通过已发布的 ZIP 链接回下载，比较大小及 SHA256，再验证 ZIP 可解压。收到上传 URL 仅表明上传成功，交付完成以发布后校验为准。
4. 回执留在 ZIP 外，记录 PR URL、附件 URL、实测 SHA、文件名、回下载结果及交付截图。报告仍是当时的验收快照。仅更新附件时按原验收 skill 维护人工验收环境。

## 异常处理

网页会话未登录时，按当前客户端流程复用已有登录会话或交接登录。GitHub API/CLI 可读取或维护描述，附件经网页选择器上传。权限或安全拦截时报告具体阻碍并交付本地证据。上传或下载失败时先确认链接和发布状态，再有限重试实际失败的步骤。发布成功但回下载受限时分别报告两项状态。发布附件、关联 Issue 和环境清理分别按用户授权及 [隔离验收流程](../isolated-app-cloud-qa/SKILL.md) 执行。
