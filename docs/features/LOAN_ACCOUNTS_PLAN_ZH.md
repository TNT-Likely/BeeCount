## 冻结结论与恢复入口

- 保留现有本金账户实现、功能测试记录与原有 issue 关联；当前成果不是完整房贷管理。
- 保留关于本息、计划、周期账单、统计、迁移和验收的完整讨论，避免恢复时只看到“贷款转账”这一部分。
- 优先待决：月供支出与消费支出的定义、是否确实需要两种还款方式、怎样减少初始化字段和每月操作。本文第 6 节的“月供计支出”只是推荐候选，不代表用户已批准。
- 其次待决：自动计算与银行实际明细的责任边界、旧估值账户接续、现有周期模板迁移和最小可用闭环。
- 恢复时先复核用户真实房贷流程和竞品实际交互，再确定产品取舍、更新技术契约及测试范围；不得直接把全部提案当作已确认需求开工。
- 没有约定恢复日期，不创建自动恢复或持续开发任务。


核心目标：用户设置一次房贷计划，继续按“银行卡每月支付月供”记账；系统处理本金、利息与剩余欠款，不要求用户每月手工拆两笔账。保留已记过原始消费的贷款所需的本金转账能力。

## 1. 当前实现的准确边界

当前 App / Cloud PR 实现了：贷款本金负债账户、同币种本金借还转账、旧余额接续、超额还本校验、余额校准与同步恢复保护。利息可另外记普通支出，但没有和一次还款关联。

尚未实现：还款总额与本息分配、还款计划、按期预填本息、月供支出关联本金、银行实际账单核对、计划变更、周期还款去重。

因此它是手动本金账户功能，不能作为本方案所指的完整房贷管理上线。原有本金与同步测试通过，也不能代替本方案的验收。

当前设计说明：`docs/features/LOAN_ACCOUNTS_ZH.md`。现有贷款校验只允许 transfer；普通 expense 不会联动减少贷款本金。现有周期服务生成普通交易，没有贷款计划与本息分配对象。

## 2. 统一对象与页面语言

- 银行卡：实际存放与扣划资金的账户，例如“杭州银行储蓄卡”。
- 贷款：欠款记录，例如“杭州银行房贷”；核心余额叫“未还本金”，不显示为可用资金。
- 还款：用户录入的一次业务操作，包含付款总额、偿还本金、支付利息及费用。
- 计划：预计未来每一期怎样还款，不代表银行已经实际扣款。

贷款继续归入负债管理；日常付款账户选择器不把贷款当成可消费的银行卡。房产等估值资产继续保留，贷款与房产估值分别管理。

如果先从工资卡转钱到杭州银行卡，只记录银行卡之间的转账，不减少房贷。杭州银行卡真正支付月供后，再记录还款。用户不需要理解“往贷款账户里存钱”。

## 3. 推荐的主要使用流程

### 3.1 初次设置：基本信息与还款计划分两步

第一步填写贷款名称、银行账单显示的当前未还本金及其基准日期、实际扣款银行卡。已有账户直接使用原 ID 与名称，不再要求新建同一笔贷款。

第二步设置还款计划：

| 信息 | 用途 |
| --- | --- |
| 当前执行年利率 | 计算预计利息，不用产品宣传利率代替 |
| 剩余还款期数 | 从当前本金向未来推演，不要求重建几十年的历史 |
| 还款方式 | 等额本息 / 等额本金 / 银行自定义计划 |
| 下次还款日 | 排定到期事项；日期可预填后确认 |
| 月供支出分类 | 默认房贷等合适分类，可使用已有自定义分类 |

本金基准、上一实际还款日与下次还款日必须匹配；中途接入、不规则首期不按完整月份硬算。可用银行后续还款计划直接建立计划；导入结果先预览确认。

没有完整参数也可以保存贷款并手动记还款，但页面明确“未设置计划”，不能声称可以自动准确拆分。已确认计划才承担自动预填功能。

### 3.2 你的已有周期账单：接续原模板

用户选中现有“每月银行卡支出”的周期模板，关联对应贷款及计划。保留原分类、扣款账户和周期偏好；将这个模板接续为贷款还款任务，不另外悄悄创建一份周期任务。

接续从指定下一期开始。已生成的历史支出保持原样，不新增补扣。系统提示疑似重复模板，由用户确定保留哪一个，不凭名称自动合并。

### 3.3 每期只有一个还款入口

贷款详情的“记还款”、到期事项、周期模板以及已有银行卡支出的“关联还款”，都进入同一个还款编辑器。

默认界面只展示：贷款、实际付款账户、本次还款总额、日期；计划存在时自动带出本期本金与利息，用一行可展开的明细展示。金额无变化时，用户确认一次即可；不要求每月分别录入本金转账和利息支出。

示例金额仅用于说明交互，不代表杭州银行的实际贷款条件：

| 本次付款 | 其中本金 | 其中利息 | 费用 |
| ---: | ---: | ---: | ---: |
| 5,000 | 3,000 | 2,000 | 0 |

按下保存后：银行卡只扣 5,000；月供支出为 5,000；未还本金只减少 3,000；流水列表显示一笔可展开的还款。利息已包含在 5,000 内，不再额外增加一笔重复费用。

关联已有银行卡支出时，复用该笔付款；不创建第二笔扣款。普通购物不因选了某个贷款标签就自动减债，必须明确转成“偿还这笔贷款”。

## 4. 本金与利息怎样自动处理

优先级：用户核对的银行实际本息明细 > 经确认的银行还款计划 > 系统计算的预计计划。保存来源、计划版本与是否核对，不能把推算伪装成银行实际数据。

- 等额本息：按当前本金、执行利率与剩余期数推算预计月供及每期本金、利息。
- 等额本金：按当前计划本金与剩余期数确定每期本金，按剩余本金推算利息。
- 自定义计划：支持用户录入或导入各期本金、利息及费用；支持零息或不等额期次。
- 月供固定不代表每期本金固定。通用周期账单不应简单把总额或上一期本金一直重复扣减。
- 金额使用十进制定点计算；精确到分，末期处理余数。零利率、尾期、月底日期单独处理。
- 常规模型只产生预计数。实际计息天数、首末期、舍入方式及银行调整造成的差异，以实际账单覆盖。

只知道实际扣款总额、既没有可靠计划也不知道本金时：先保留真实付款支出，标记“本金待核对”，未还本金不凭猜测减少，显示余额覆盖日期。用户补齐本息后，在原还款上完成分配，不新增付款。

已确认欠息、罚息与费用和本金分开记录；未来预计利息不直接计入当前未还本金或当前负债。需要展示已确认未付费用时单列，实际结清时一起处理，不把费用变成本金。

## 5. 周期记账、自动化与实际扣款

计划先生成到期事项；未入账计划不影响银行卡余额、贷款余额或已发生支出。

- 普通使用：到期确认一次，自动带出本息。
- 用户启用自动入账：按计划产生还款，明确标识“按计划生成、未核对”；沿用用户已有周期自动记账偏好。没有银行确认时，不显示“银行已扣款”。
- 无计划或本息数据不足：产生待处理事项，不把全部月供当成本金自动扣减。
- 自动生成之后导入实际银行流水：匹配到既有还款，核对或修正原记录，不再生成一笔支出。
- 日期、金额、账户相近只能给匹配候选；不确定时让用户确认关联，不能错误吞掉另一笔真实付款。
- 到期自动记账沿用周期引擎的实际触发条件；若依赖 App 启动补生成，需准确告知，不承诺系统没有的后台执行或银行同步能力。

同一期的身份在计划修改前后保持稳定；计划版本、日期变化不能导致同一期重记。多个设备重复触发、离线生成后同步、服务重试都须幂等。提前结清后停止后续到期任务。

## 6. 统计口径：集中在记账时处理

推荐新房贷/车贷的主要流程采用“按月供记支出”，对应你目前的记账习惯。还款支出表示本期付款用途，本金减债独立反映在资产负债中，因此支出总额不等于净资产减少额。

| 事件 | 银行卡 | 未还本金 | 普通收支/预算 |
| --- | --- | --- | --- |
| 备款：工资卡转入扣款卡 | 两卡之间转移 | 不变 | 不计 |
| 月供 5,000，其中本金 3,000、利息 2,000 | 减少 5,000 | 减少 3,000 | 记 5,000 普通支出 |
| 借款实际到账 | 增加放款额 | 增加借款额 | 不记普通收入 |
| 校准未还本金 | 不变 | 按核对记录调整 | 不计 |
| 未来计划 | 不变 | 不变 | 不计已发生收支 |

已经把原始购置或消费完整记过支出的贷款，仍需支持“本金转账、费用记支出”的处理，防止重复。放在贷款还款设置里一次确定，以后还款沿用；不在首页、洞察、预算、导出等页面各加开关。迁移既有记录时保留原统计行为，不能把所有旧转账自动变成支出。

具体实现必须让还款操作在写入时生成普通支出/转账及关联本金变动；统计继续消费统一的普通交易结果。不要在每个统计查询中分别增加“遇到贷款转账就当支出”的判断。

主流程为一笔普通支出关联本金变动；本金变动不再从银行卡扣一次款，也不是第二笔支出。另一种处理生成本金转账及利息费用支出，统一归属一次还款。既有收支排除、预算排除、汇率快照规则继续有效。

设置变更仅影响指定生效日之后的新还款，历史金额、分类与统计不可静默改写。用户可以按本息组成查看分析，但总支出和本金明细不能重复累加。

## 7. 必须完成的异常与计划变更

| 场景 | 产品行为 |
| --- | --- |
| 实际月供与预计不同 | 支持核对本期实际本息；只改总额时不能自动猜差额都属于本金或利息 |
| 利率调整 | 录入生效期及新的执行条件；重算尚未发生的计划，保留已确认历史；银行新计划优先 |
| 提前部分还款 | 本次本金、实际利息/费用分开；按银行结果选择后续减少月供或缩短期限，更新预计计划 |
| 提前结清 | 核对结清本金与费用，结清后停止未来任务，保留历史并可归档 |
| 跳过一期或扣款失败 | 保持未支付状态，不自动减本金；再次付款后关联原期次 |
| 实际还款无法覆盖应付利息 | 进入待核对，不产生负数本金或自行判断欠息资本化 |
| 本金超过当前欠款 | 阻止直接形成正数贷款余额，要求核对结清金额；不静默裁剪真实付款 |
| 手工校准余额 | 新增可追溯的核对调整，不影响银行卡与普通支出，不伪装成还款 |
| 修改/删除还款 | 付款、本金、费用关联更新或撤销；不留下少扣现金、多减本金的半笔账 |
| 修改较早还款 | 预览对本金与未来计划的影响；后续已确认付款不自动改写；出现冲突先核对 |
| 银行退款或撤销 | 回退对应本息组成；恢复本金与付款账户，按原支出规则冲减，不误记一笔收入 |
| 隐藏/删除贷款或付款账户 | 有未完成计划时明确处理任务；保留历史引用，结清优先归档 |
| 组合贷 | 商贷、公积金贷独立本金与计划，支持归为同一组；合并扣款需明确分配到各笔贷款 |

## 8. 旧贷款、估值体系与历史兼容

1. 继续保留房产、车辆等估值账户；它们不因贷款升级变成付款账户。
2. 老贷款允许继续只维护当前欠款快照。升级不应强制启用还款计划或改掉原周期支出。
3. 启用还款管理时，核对当前未还本金、余额基准日期、已记录支出的方式，以及准备接续的周期模板。
4. 保留原账户 ID、币种、名称、隐藏状态、备注与历史；同一笔贷款只保留一份当前负债，不能旧估值与新本金账户各算一次。
5. 新的自动减本金从接续起点开始。接续前的支出可以展示关联，但它们已包含在当前本金快照中，不能再次减债。
6. 新建了重复贷款的用户可预览并选择接续到哪份记录；不自动按名称合并，也不伪造一笔转账来消除重复。
7. 当前 PR 中“无关联历史则自动接续”的策略需要重新评审：普通周期支出可能根本没有贷款关联，不能据此认定用户没有原有记账方式。
8. 银行直接向卖家放款的历史房贷，只登记真实当前本金即可，不要求伪造一笔银行卡先收入、再消费的历史。

## 9. 实现契约与双端一致性

必须保存可追溯的贷款计划、还款业务对象、付款交易关联、本金/费用分配、核对来源与生效版本。精确字段与数据库迁移在技术评审时定稿。

- 还款是一个完整操作。创建、编辑、删除以及周期进度更新保持事务完整；同步及快照恢复也必须整体校验，不因传输分批先展示半笔账。
- 所有入口共用同一套本息计算、舍入与保存校验；App/Web 的同一期输入产生同样结果。不能只在 Flutter UI 侧算对。
- 银行卡和本金余额从可重放记录计算；禁止每次保存时暗中修改贷款初始余额来代替本金记录。
- 月供业务分配使用交易原币，支出折算复用既有记账汇率快照。首版个人账本、同币种付款约束显式保留；跨币种还款需独立设计本金汇率关系。
- 同一期生成、离线重试和导入核对共享稳定业务身份。修改计划不能生成新身份导致重复扣款。
- 导出包含可读总额、本金、利息、费用、贷款与付款关联；原生备份可完整恢复。只有普通流水的导入不能凭备注推断本金。
- API/MCP、App、Web、同步与恢复升级能力契约。旧客户端即使只编辑来源为银行卡的普通支出，也不能绕过关联还款的保护。
- Cloud 先具备新契约，再放开客户端写入。已升级贷款数据不能被旧客户端降级覆盖。

## 10. 交付顺序与完成标准

阶段 A：还款业务对象、普通交易投影、关联本金变动、计算引擎与同步契约。

阶段 B：一次设置计划、统一还款表单、现有周期模板接续、到期处理、银行流水核对与主要计划变更。

阶段 C：旧账户迁移、历史保护、双端回归、备份恢复与可交付验收报告。

以上是一个完整可用版本的组成部分，不应只完成 A 就把手工本金账户称作完整房贷管理。自动识别更多银行截图、银行直连、额外图表可以继续增强，但不应成为正常还款必须依赖的条件。

按当前用户目标，现有 App #566 / Cloud #130 不宜原样作为完整贷款功能合并；先按本方案重评范围与验证。冻结交付只沉淀文档、更新两份 PR 的 WIP 状态；业务实现与运行中的验收数据不因本文而改变。

### 必须通过的验收场景

- 两种标准还款方式、零利率、尾期分币舍入、非标准首期。
- 月供总额与本金/利息/费用一致；银行卡一次扣款，贷款只减本金。
- 月供计支出与原消费已计支出的处理，收支/分类/预算/趋势/导出一致。
- 原周期账单接续、未开启自动记账、开启自动记账、无计划待核对。
- App/Web 相互新增、修改、删除、离线同步、同一期多端重复生成。
- 银行流水导入先于或晚于自动记账，明确匹配与无法确定匹配。
- 利率变化、提前还款、跳期、失败、结清、退款、欠息待核对。
- 接续前历史不重复减本金，旧估值贷款保留，重复账户不重复计负债。
- 普通收入/支出/转账、信用卡消费/还款、房产估值与现有周期账单回归。
- 快照备份恢复、旧客户端拦截、失败重试、重启后本息与余额一致。

实施验收继续使用用户已指定的 isolated-app-cloud-qa 工作流：独立 App 包、专用模拟器、新 Cloud 数据库、合成数据、真实双端 UI、双向同步、失败恢复与独立报告。现有手工验收环境的数据不作为可重复播种的测试夹具。
