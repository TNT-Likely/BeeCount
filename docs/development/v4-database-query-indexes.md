# V4 大数据列表：补齐开库性能索引

## 发现与范围

R119 的同一隔离安卓真机经生产 UI 一次导入 15000 笔后，交易写入阶段为 24.450 秒，从旧账本切回压力账本的完整截图上界为 11.339 秒，未达到 2 秒目标。该候选的失败证据保持原样，不能用后续修复覆盖。

对冻结的 SQLite、WAL、SHM 建立私有工作副本，再通过 SQLite backup API 生成稳定分析库；原文件 SHA256 未变，分析库全部 31 表的值与冻结快照一致。实际 schema 为 33，交易 15072 笔、标签关系 63140 条。交易、标签关系、附件、账户、分类、标签、预算和账本均缺少性能索引：标签 JOIN 扫全表，首页扫交易表后另建临时排序树。

原因是 12 项性能索引仅在旧版本 `onUpgrade` 分支中创建。`onCreate` 的 `createAll()` 不会执行那些历史分支，直接创建的 v33，以及以后继续使用该 v33 的数据库都会遗漏它们。

## 修复

`BeeDatabase.beforeOpen` 幂等创建下列非唯一索引，覆盖新建、升级和已有 v33 开库。不修改 schema 版本、行数据、唯一性约束、外汇或统计规则。

| 表 | 索引列 | 来源 |
| --- | --- | --- |
| transaction_tags | transaction_id、tag_id，各一项 | 恢复历史迁移两项 |
| transaction_attachments | transaction_id | 恢复历史迁移 |
| transactions | sync_id | 恢复历史迁移 |
| accounts、categories、tags、ledgers | 各表 sync_id | 恢复历史迁移四项 |
| budgets | sync_id、ledger_id、category_id、(ledger_id,type) | 恢复历史迁移四项 |
| transactions | (ledger_id,happened_at DESC) | 新增一项，对应真实首页筛选与排序 |

新增 schema 对象白名单共 13 项，仅索引。已有同名索引通过 `IF NOT EXISTS` 保持；没有新增分页，也没有为回避加载而减少日汇总或完整记录范围。

## 回归证据

- 新建 v33 已有索引，标签、附件和首页查询使用索引，首页不再额外建排序树。
- 已有 v33 缺索引库经真实开库补齐；全部 31 表原值不变；连续三次重开索引定义与数据保持一致。
- 实际 v32 → v33 升级保留历史索引、全部原值及正常升级行为。
- 在真机冻结数据的独立副本上调用实际 `BeeDatabase.beforeOpen`，再重开；15072 笔交易、63140 条标签关系和全部 31 表逐值相同。独立 Python 再核全部表 hash 与原冻结快照一致。
- 目标回归 22 项通过，包含上述完整副本专项 1 项；提交内常规测试 21 项。之前单独跑过的 3 项不重复累计。静态分析无 error/warning，数据库旧代码保留 41 项既有 info。

这证明查询计划与数据保护正确，不代表新包真机性能已通过。后续在同一压力账本上验证独立 AOT 候选，继续单列冷启框架异常和端到端时间；不得再次导入同一文件变成 30000 笔。
